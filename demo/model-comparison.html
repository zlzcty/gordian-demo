Seven LLMs vs. one floating-point logic bomb

We ran Gordian's lb_float1_fp_l1 benchmark with seven different models writing the ghost code. Six reached full coverage. They differed a lot in how fast they got there and how many tokens it took.

Claude Opus 5.5 · Sonnet 5.5 · Haiku 5.5 GPT-6.1 Sol (Codex) DeepSeek V4.1 Flash · gpt-oss-20b · Mistral Nemo

The verdict

▲ Best overall
DeepSeek V4.1 Flash
  • 13/13 lines in 43 s end to end, the fastest run. The bomb line was covered by the first harness, at 32 s.
  • One API call of 19.8 s using 9,481 tokens in total. The Claude Code runs used 440K to 1.5M.
  • Its first harness fixed s[0] = '7' before any float math ran. That is exactly the input the bomb needs.
▼ Worst
Mistral Nemo
  • The only model that missed the bomb: 12/13 lines (92.3%). Line 13 was never covered.
  • Its harnesses tried s[0] = '1', '2', '3' and then constrained s[1] and s[2], bytes the function never reads. It never tried '7'.
  • The fallback surrogate model failed to compile, and so did its repair. Gordian ran out of ideas.

Ranking rule: coverage first, then time until 13/13, then LLM effort (tokens, turns). Six models tie on coverage, so speed and efficiency decide the order.

Background

What Gordian is

Gordian is a layer on top of KLEE, a symbolic execution engine that explores a C program's paths and generates test inputs for them. KLEE struggles with code that is hard for its constraint solver: floating-point math, crypto, heap shapes, parsers. Gordian has an LLM write ghost code, temporary scaffolding that makes those spots tractable. KLEE then explores the scaffolded program, and every test it produces is replayed on the unmodified program. Only coverage measured on the original code counts.

A run moves through four stages. Each stage only works on what is still uncovered, so a run that hits 100% early skips the rest.

stage 0Explore

A short plain-KLEE run on the original program. It finds the uncovered lines.

stage 1Partition

The LLM writes 3 harnesses. Each splits the input into a few concrete "classes" chosen to reach the uncovered lines.

stage 2Rewrite

The LLM triages what is left and writes a solver-friendly surrogate of the hard code.

stage 3Inversion

For invertible computations: replace the code with a havoc and solve backwards from the target.

The target

Why this bomb is hard

lb_float1_fp_l1 is a "logic bomb" from the LogicBombs suite. The goal is to reach return BOMB_ENDING on line 13.

Only one input works: s[0] == '7'. Then 7/70.0 is the double 0.1, which rounds to the float 0.100000001490116…. That float is not equal to the double 0.1, so the outer if passes. But a - b subtracts two identical floats and gives 0, so the bomb fires.

Standard KLEE picks one concrete value for a symbolic number as soon as it reaches floating-point math. So the explore stage tries a single s[0], takes the normal path, and covers 12 of 13 lines in about 10 s. To win, the LLM has to notice that '7' is the magic byte and pin it in a harness before the float operations run.

// {"s":{"length": 4}}int logic_bomb(char* s) {    int symvar = s[0] - 48;    float a = symvar/70.0;    float b = 0.1;    if(a != 0.1){        if(a - b == 0)            return BOMB_ENDING;← the one line explore can't reach    }    return NORMAL_ENDING;}int main(int argc, char** argv) {    char s[5];    klee_make_symbolic(&s, sizeof(s), "s");    klee_assume(s[4]=='\0');    return logic_bomb(s);}
Reading a report

What each result means

Every run folder has a report.md. These are its fields.

line coverage
Lines of the original float1_fp_l1_klee.c executed by the replayed tests. 13 lines are coverable, so 13/13 means the bomb line ran and 12/13 means it never did.
test cases
The number of KLEE test inputs (.ktest files) kept across all stages. More is not better here. Six cases are enough if one of them has s[0]='7'.
bombs reached: 0
This is 0 for every run, including the winners, and it is not a failure. The counter only picks up a GORDIAN_BOMB_REACHED marker printed during replay. This bomb signals by returning BOMB_ENDING (3) instead, so covering line 13 is the proof that it fired.
LLM usage
Input and output tokens summed over all LLM calls in the run. calls counts Gordian tasks, not agent turns. One Claude Code task can be 5 to 20 turns.
00_explore
The plain-KLEE baseline. It gave 1 test and 12/13 lines in every run.
01_partition_N
KLEE run on the LLM's harness number N. ktests = tests it produced; new lines = lines no earlier step covered; t = seconds since the run started.
02_model_*
The rewrite stage's surrogate model. It only appears for Mistral Nemo, the one run where partitioning failed. build failed means the generated C did not compile.
triage
The LLM's routing of each leftover region to model or inversion, with a confidence score and a reason.

Caveats

  • One target, one run each. This is a 13-line program. It shows whether a model spots the magic byte, not how it handles a parser or a math library. Run-to-run variance is unmeasured.
  • Two machines. The Claude runs were made on one machine (Oct 25) and the Codex/OpenRouter runs on another (Oct 23). Explore took 5–11 s on both, so the hardware gap is small next to the LLM-time differences.
  • Agents did more checking. Opus brute-forced every char in Python to prove '7' is the only trigger, then syntax-checked its harnesses in WSL. Single-shot API models can't run anything, so their speed partly comes from skipping verification.
  • Stray files in the DeepSeek folder. deepseek_v4.1_flash_1017/ reused a Mistral run directory (float1-nemo-1). Its 02_rewrite/, triage and 0004/0005 LLM files are Mistral Nemo leftovers. DeepSeek's own report counts only its single partition call.
